# WhaleGenie 开发路线图

本文件只记录尚未完成的工作、待评估事项和产品非目标。长期规范见
[AGENTS.md](../AGENTS.md)，开发与验收命令见 [dev.md](dev.md)，当前实现见
[architecture.md](architecture.md)，已实现的用户行为见 [manual.md](manual.md)。

## 规划规则

- 阶段完成后删除对应内容，变更历史由 git 保存。
- 一个阶段只解决一类问题，并具有明确的依赖、修改范围、自动化验收和必要的手动验收。
- 不记录工期。优先级依次考虑：用户能否表达需求、文档与实现是否一致、多条宏同时运行是否正确。
- 先处理契约和静默错误，再处理行为扩展与操作便利；游戏与办公场景具有同等优先级。
- 待评估事项必须先取得测量结果，再决定是否升级为阶段。

## 阶段

阶段按顺序实施。每一阶段只解决一类问题，完成后删除本节对应内容。

### 值的形状边界与往返法则（进行中）

**问题**：动作表单把显示文本当成模型值回写。区域行的变量/公式与四个数字、子宏调用参数、图片名在确认表单
或页面补丁后变成字面量；`FormulaJson.Read` 对内存中的 decimal 数字回退成文本。两者都在保存时发生、
重开时才发现，运行期表现为 `Run.BadRegion` 或看向错误的位置。复现与根因见
[ADR 0003](adr/0003-value-shape-boundary.md)。

**目标**：文件、编辑器、线缆三层往返后，值仍是同一个形状；“用显示文本回写模型”在类型上写不出来。

**范围**：Core 的 `FormulaJson` 与值法则；Domain 的步骤参数编解码；Editing 的行、表单与纯草稿；
Contracts 的行载荷；webui 行编辑器；两个仓库的测试与只读扫描工具。引擎、动作语义、包格式不动。

**两仓顺序**：

1. 库仓 [ilpoint/WhaleGenie.Core](https://github.com/ilpoint/WhaleGenie.Core)：`FormulaJson.Read` 的数字分支与
   L1/L2；按库仓 README 的命令构建、测试；公共面不变。
2. 主仓：按 [dev/environment.md](dev/environment.md) 的 subtree/`sync-core` 流程取回；再做 Domain 的 L3/L4、
   Editing 的 L5、Contracts/webui 的 L6。`core/` 在主仓只读，不在主仓提交库仓改动。

**阶段**：

- **A 止血**：Core 数字分支；区域、调用参数与图片行保留 `ExpressionNode`；`PatchRow` 与内联编辑走
  `Write`；删除模型路径上的 `SetLine`。先写失败用例再改。
- **B 法则**：Domain 的 L3/L4 生成器（目录里的全部动作 × 参数 × 值形态）；Editing 的 L5；桥的 L6。先跑出
  失败清单，再逐项修。
- **C 线缆**：行单元格带 `EditorValuePartSnapshot`；`ContractsGen` 重新生成 TS；页面复用标量字段的
  parts 编辑器；未编辑的单元格不回传。
- **D 收尾**：只读扫描器列出已坏工程的可疑行（不自动改）；包往返与行往返的自动化用例；三处手工
  变异确认法则能变红；更新架构与测试文档。

**验收**：

- ADR 0003 的 L1–L6 全绿（L3/L5 比较模型形状，不只文件 JSON）；库仓与主仓的全部套件绿；
  Core 公共面基线不变。
- 以源码检索为准，模型路径上不再有 `SetLine` 与行级 `.Text =` 回写。
- 扫描器能列出已坏工程的可疑行；包往返与行往返的自动化用例全绿；手工变异三项均被法则杀掉。
- 契约生成一致（`ContractGenerationTests`）；网页行编辑不再丢名字或公式。

**剩余**：真实场景的 10 个宏手动验收；把行变换从行 VM 抽成纯文件后，Editing 的变异门禁收到 100%
（当前 Stryker 基线 31.43%；Domain 100%，库仓 FormulaJson 91.67%）。自动化部分与一个真实项目包的扫描已完成。

**边界**：不做引擎运行时重写（归“函数式核心与命令式外壳”阶段）、不做动作合并、不做旧格式迁移、
不新增产品工程、不在页面里复制形状代数。

**文档**：决定与法则见 [ADR 0003](adr/0003-value-shape-boundary.md)；实现落地后更新
[architecture.md](architecture.md) 与 [dev/testing.md](dev/testing.md)。阶段完成即删除本节。

### 函数式核心与命令式外壳（进行中）

**实现状态**：`TransferPlanner` 是包转移的纯核心（计划行、冲突、选择、决定、报告）；`PackageShapeReader`、
`PackageManifestBuilder`、`PackageReadme` 把包形状、manifest 与 README 从 ZIP/时钟外壳中拆出；
`McpDraftRules` 是草稿校验的纯核心，`McpPreview.Of` 的列表版本把 diff 也从草稿锁中拆出；子宏删除判断
`SubMacroEditor.CanDelete` 与列表修改分开。纯核心测试不需要文件、工程、草稿会话或时钟。运行时的纯化排在“值的形状边界”之后；包、MCP 与编辑器的纯核心已经落地，不受影响。

**下一步**：

- 继续把包 codec 的节点文档组装/资源收集边界收紧，`FilePackageStore` 只保留 zip、资源解包、
  临时文件与备份；
- MCP 草稿的客户端 JSON 解析与 diff 只留纯函数，宿主保留权限、审计与 revision 闸门；
- 编辑器只继续抽步骤树、子宏复制/改名的纯变换，`EditorDocumentSet`/会话仍保持命令式外壳。

**边界**：宏运行时、输入/画面/窗口设备、UI 状态机、文件选择器和 WebView 留在外壳；不为了纯函数
复制每帧画面或整棵步骤树。新增纯核心不读写文件、不依赖当前时间/随机 ID，测试以记录和列表为输入。

## 待评估

以下事项尚未承诺实施。升级为阶段前须写明测量结果、目标、范围和验收方法。

### 结构与诊断

- **编辑器多文档崩溃恢复**：网页编辑器可同时打开父宏与子宏，当前恢复文件只覆盖工程包；关闭或崩溃时
  未提交的编辑器草稿不在里面。前提是 `EditorDocumentSet` 能导出各文档的完整草稿与父子关系，恢复文件
  需要一个版本化的 `editor.documents` 数组（不兼容旧形状），并决定子宏草稿随父宏恢复的顺序。验收：
  打开父宏与子宏各改一处、结束进程、下次启动恢复后两份草稿与页签关系都在，工程仍保持原版本。
- **保存冲突的另存为新宏**：目标宏在别处被改过或删除时，编辑器保留脏状态并显示冲突原因，但还不能
  一键把草稿作为新宏提交；当前只能导出或从宏列表重新打开。前提是给文档命令一个“解除绑定并新增”的
  结局（父/子文档的归属要先定），验收是在 MCP 替换目标宏后保存、选择另存为新宏，草稿进入工程且
  页签继续指向新宏。
- **无界面命令行**：`Models/`、`Storage/`、`Localization/` 已出界面工程，但只服务 MCP 与包读写；
  仍不新增 CLI 入口，除非出现 CI 批量验包、脚本生成宏等真实调用方。
- **文件读写失败细分与撞名策略**（见下节两条）：要动 `ActionSemantics.json`、`RunVocabulary` 与
  引擎，归属 vendored 的 `core/` 仓库，按 AGENTS.md 的 subtree 规则在那边立项，不在这里改。

### 动作与编辑器表达

2026-11 收尾时决定保留现状的三项：`control.ask`（等回答）与 `control.input`（读字段）是两种交互，
`control.note` 进运行日志而步骤备注只属于编辑态；变量写入的多个动作按目标不同分开；子宏 Dock 已有
页面入口。`process.start` / `command.run` 的选择是**不做**编辑期命令行预览——引擎按三个字段取值，
预览只能显示拼好的字面量，无法诚实表示变量。

- **列表动作的行表**：`control.listAdd` / `listInsert` / `listSet` 只有一格 `value`，`control.forEach`
  的 `items` 也只有一格整值，编辑期看不见目标列表里已有什么、也不能一次给多项。前提是先弄清「看见已有
  条目」与「一次给多项」是不是同一件事；验收要有真实宏说明需要哪一种。

### 补动作与参数

对照同类软件（大漠与按键精灵的找图、UiPath 与 Playwright 的元素、AHK 与 PAD 的脚本、文件与系统）
逐项比过之后留下的缺口。逐条写明现状、前提和验收；补完一条删一条。

- **文件撞名的策略统一**：`file.copy` / `file.move` 是三选一 `ifExists`（覆盖 / 跳过 / 换个名字），
  `file.unzip` 只有一个 `overwrite` 开关且默认开，`file.writeJson` 没有任何策略——它恒定读旧文件、
  合并键、整份写回。前提是先定这三处的词是不是同一套；验收是三个动作在同一份宏里对同一个目标各跑一次。
- **文件读写失败的细分**：现在只有 `Run.FileFailed` 与 `Run.FileNotFound`，分不出被占用、没权限、
  磁盘满。前提是先定这层信息是「新的失败键族」，还是「像脚本那样多一条 `error` 结果」——结构列讲的是
  值的形状，塞不进失败键。

## 产品非目标与暂不计划

以下事项不属于当前产品方向。重新提出时须说明前提变化、真实使用场景和可验收收益。

- **防检测与隐藏**：不读取其他程序内存、不修改其程序包，不提供驱动级隐藏。VIIPER 仅作为输入通道。
- **专用验证靶场**：不在产品或测试中恢复只验证自身的靶场窗口；真实输入使用现有桌面程序验收。
- **多尺度模板匹配**：分辨率变化时使用相应参考图，不引入自动多尺度匹配。
- **`dir` 0–8 那套方向**：不照搬。找图与检测给四向 + 综合评分 + 离指定点/画面中心最近 + 随机；
  颜色族只有四向（命中是一像素，面积与分数没有意义）。「从中心向外」在找图上按距离做，不按螺旋扫描。
- **PNG 的 alpha**：找图的透明色只认两条——写下来的颜色（可以写多个）与「四角同色自动识别」，不按
  alpha 通道判。按 alpha 要把参考图的解码从彩色改掉，会动到所有参考图。
- **多锚点**：元素锚点只给一个。「在『确定』右边」一个够用，两个锚点会让查询结构再长一层。
- **网页的 strict 模式**：多个命中不报错，用 `matchIndex` 取第几个，默认第一个。
- **注册表的其它根**：只给当前用户与这台机器；HKCR、HKU 那几处改的是「每个程序都照它办」。
- **条件里直接问窗口与进程**：要么先加一步（`window.exists` / `process.exists`）再比它写出来的变量，
  要么给表达式开宿主函数的口子——后者要让 Core 的表达式表接设备，而 `while` / 等待直到是 30 毫秒一轮
  的，每轮跨进程查一次窗口足以拖死程序。只给左值：`sys.activeWindow`、`sys.activeProcess`。
- **屏幕分辨率与默认打印机**：前者改整台机器的显示方式，后者要配合「打印一份文档」才自洽。
- **办公文档与企业系统解析**：不内置 PDF、Word、工作簿或企业系统连接器；数据文件聚焦 CSV、JSON
  和纯文本。通用 HTTP、数据库和邮件动作也需有反复出现的真实流程后再评估。
- **第二套流程机制**：不引入宏内并行块、从块内失败点继续或替代块结构的流程系统；并发由多个宏表达。
- **浏览器多实例**：同一时刻保持一份浏览器，通过标签页和浏览器门管理操作。
- **额外记录访问语法**：不增加 `x(记录)`、`y(记录)`、`point(记录)` 或 UIA 运行时句柄持久化；
  使用现有 `field()`、位置/矩形字段和稳定窗口规则。
- **完整静态类型系统**：只进行目录声明支持的类型检查，不做类型推导。
- **物理单位与 DPI 换算**：坐标与尺寸统一使用屏幕像素。
- **自动记住动作表单输入**：重新打开动作时使用默认值；需要复用时复制步骤。
