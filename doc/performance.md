# 性能测试

[简体中文](performance.md) | [English](performance.en.md)

"看一次屏幕"要花多少时间，以及这些数字是在哪台机器上、用什么办法量出来的。它不随 CI 跑：改动画面获取
（`WindowsScreenDevice`）或匹配与识别（`OpenCvVisionDevice`、`PixelSearch`、`PaddleOcrDevice`）之后，
在这里留一笔新的，好跟改动前比。数字之外的事情——谁读屏幕、什么时候读——见 [README.md](../README.md)
的「画面从哪来、怎么取」。

## 怎么量的

- 机器：桌面 2560×1440，16 核，Windows，`net10.0-windows10.0.19041` 的 Release 构建。
- 办法：临时建一个引用 `WhaleGenie.Core` 的小程序，直接用引擎自己的设备——`WindowsDeviceLayer` 的
  `Screen` / `Vision` / `Ocr`，与运行时走的是同一条路。每项先空跑一次热身，再取 6–15 次的中位数。小程序
  量完就删，不进仓库。
- 参考图是当场从整屏上裁下来的 200×80 一块，所以它一定找得到，量到的是"找得到"这一路的成本。
- 这些是这一台机器上的量级：换分辨率、换显卡、换 CPU 都会变。比数字本身更值得记住的是它们之间的比例。

## 抓一张画面

| 怎么抓 | 中位数 | 最快 / 最慢 |
| --- | --- | --- |
| 整屏 2560×1440，桌面复制（显卡交出的整块画面，画面重画过） | 2.0 ms | 0.5 / 7.6 |
| 同上，画面没有重画过（给的是手里那张） | 0.1 ms | 0.1 / 0.2 |
| 400×300，桌面复制 | 0.1 ms | 0.1 / 0.4 |
| 整屏 2560×1440，桌面（GDI） | 29.5 ms | 24.6 / 32.5 |
| 一小块 400×300，桌面（GDI） | 4.4 ms | 3.4 / 7.2 |
| 整屏 2560×1440，整屏（Graphics Capture，不能桌面复制时才走的库那一路） | 18 ms | 13 / 24 |
| 同上，每次读都开关会话 | 51 ms | 48 / 54 |
| 一个铺满屏幕的窗口 2576×1416，窗口（PrintWindow） | 20 ms | 16 / 28 |
| 同一个窗口缩到 900×650，窗口（PrintWindow） | 4 ms | 3.6 / 5.5 |
| 一个窗口 800×600，窗口（Graphics Capture） | 10 ms | 8 / 11 |

整屏最快的一条路是**桌面复制**（DXGI Desktop Duplication）：显卡正在往显示器合成的画面被复制进我们自己的
纹理里，读出来就是屏幕上那一张。画面重画过就付一次 14.7 MB 的搬运，2560×1440 是 2 毫秒，比 GDI 复制屏幕
快十几倍，并且独占全屏的游戏只有它能取到（GDI 给的是黑屏）。它还是唯一"画面没重画就白拿"的一条路：桌面
没动过就没有新帧，手里那张就是屏幕上那张，再要一次只要 0.1 毫秒——引擎里一次整屏"看"多数落在这一档上。
代价是每个进程第一次要建一次显卡设备（0.25 秒上下，一次运行付一次），而且显示器开着 HDR、或者屏幕是转着
用的时侯它读不了，那时整屏（Graphics Capture）退回库那一路（18 毫秒，见下表），再不行退回 GDI。

GDI 这一路抓一次的成本跟"抓多大"走：抓整屏要把 2560×1440×4 ≈ 14.7 MB 从显示设备搬进内存，抓 400×300
只有它的十五分之一；那 29 毫秒里绝大部分是这次搬运（单独量 BitBlt 约 16 毫秒，取回内存 0.6 毫秒，分配
输出缓冲 0.6 毫秒）。桌面复制反过来跟抓多大没关系：它每次都要拿整块屏再裁出你要的那块，所以 400×300 与
整屏同一价钱（2 毫秒，画面没重画时 0.1 毫秒）。要一小块，GDI 那一路 4 毫秒也够快，好处是不用先建显卡
设备；所以抓得少、跑得短的宏，勾"桌面（GDI）"反而更划算。窗口（PrintWindow）这一路是靠请窗口把自己重画
一遍，所以也跟窗口多大走：铺满屏幕的窗口 20 毫秒，缩到 900×650 只要 4 毫秒。

**窗口那一路的会话要留着**：开一个会话（建显示设备与帧池）第一次要 0.4 秒，此后每一帧只是一次显存到内存
的搬运，所以留着会话时读一个窗口 10 毫秒、读整屏 18 毫秒；读一次就开关一次则要 51 毫秒，是前者的三倍上下。
Windows 还会在正在被读的窗口四周画一圈捕获提示边框，会话开着就在、关掉就没——**每次读都开关会话，边框
就会跟着一闪一闪**，这也是它必须留着的一个理由。分层窗口、系统设置页、输入法候选框、显卡的覆盖层这些库
根本认不出的窗口只在第一次试一下就被记下来，不去为它们反复开关会话。

## 在画面里找东西

参考图 200×80，画面都是整屏 2560×1440，除了注明的那一行：

| 找什么 | 中位数 |
| --- | --- |
| 找图，归一化相关 | 211 ms |
| 找图，相关 | 202 ms |
| 找图，平方差 | 201 ms |
| 找图，特征比对 | 281 ms |
| 找图，只在 640×480 里找（归一化相关） | 14 ms |
| 找色，颜色出现在画面开头 | ~0 ms |
| 找色，颜色不在画面上（走完全幅） | 2.5 ms |
| 找色，要离颜色最近的 20 个（走完全幅） | 11.9 ms |
| 找色并算占比，整屏（找一遍，再走一遍数像素） | 4.3 ms |
| 找色并算占比，400×300 | 0.2 ms |
| 多点找色，400×300（三个点，颜色不在画面上） | 0.2 ms |
| 判断画面有没有动（等画面静止的每一轮） | 5.7 ms |
| 文字识别，整屏 | 128 ms |
| 文字识别，800×200 | 23 ms |

- 找图的成本跟"搜索面积 × 参考图面积"走：整屏里找 200×80 是 211 毫秒，同一块参考图收进 640×480 去找
  只剩 14 毫秒，十五分之一。**把区域收小是这里最大的一根杠杆**，比换算法、比少抓一次屏都管用。
- 找色只看单个像素：命中出现得越早越便宜（第一个像素就中，量到 0 毫秒）；要"离颜色最近的几个"就得走完
  整幅，那是 12 毫秒。颜色根本不在画面上时，一次注定落空的查找是 2.5 毫秒。这两处都比改前快六倍上下，来得
  自同一件事：一个像素的颜色是否算数，看的是三个通道的平方和，与看距离是同一个问题，而由距离求值要开一次
  平方根，那一步是每个像素都要付的（同一条路 14.5 → 2.5 毫秒）。要"离颜色最近的几个"时比的是平方和，排
  出来的次序与按距离排一样，所以最贵的这一行也从 30 毫秒降到 12 毫秒。
- 算占比与多点找色都是把整块区域走一遍：整屏 2560×1440 数一遍是 2.5 毫秒，"找一遍再数一遍"是 4.3 毫秒；
  400×300 只要 0.2 毫秒。条件「颜色占比达到」走的是同一趟，所以它跟查找颜色问占比一样贵。**占比只在步骤
  真的问它时才数**，没问的步骤还是走"命中即返回"的那条路。
- 找色也量过 OpenCV 那条路（`InRange` 加 `CountNonZero`）。整屏数一遍 2.7 毫秒，与手写的平方和走法
  2.5 毫秒同一量级，但它比的是每个通道各给一个上下限的方框，与引擎的圆规则不是同一个判据：宽容度 5% 时
  多算 683 个像素，而引擎认的是 249 个；要拿回同一个答案还得在方框里再走一遍，共 3.8 毫秒。多点找色的
  三个点用 OpenCV 是三次 `InRange` 加两次按位与，400×300 上是 1.96 毫秒，比手写的 0.2 毫秒贵十倍，而且
  只说出"有几个"，要位置还得再找一遍。所以这条路没有走。
- 文字识别第一次调用要 1.1–10.3 秒把模型读进来（取决于磁盘缓存有多热），之后才是 128 毫秒。整屏识别是
  这里最贵的一次"看"。

## 一次"看"合起来是多少

一次"看" = 抓一次画面 + 在上面做一次算法。默认值下（`frameMaxAgeMs` 为 0、`intervalMs` 为 0）每看一次就
重抓一次，于是：

| 做法 | 一次 | 每秒 |
| --- | --- | --- |
| 整屏找图 200×80 | 2.0 + 211 ≈ 213 ms | 约 5 次 |
| 同一件事只在 640×480 里找 | 4.4 + 14 ≈ 18 ms | 约 55 次 |
| 整屏找色（命中早） | 2.0 + 0.4 ≈ 2.4 ms | 约 400 次 |
| 整屏文字识别 | 2.0 + 128 ≈ 130 ms | 约 8 次 |
| 等画面静止的每一轮 | 2.0 + 5.7 ≈ 8 ms | 约 125 次 |

两个能改变这个数的开关，都在「高级设置」里，默认都是关的：

- **接受多久以内的画面**（`frameMaxAgeMs`）：大于 0 时，同一次运行里同一来源、同一抓法的画面只抓一次，
  后面的步骤从这张画面上裁自己要的那块。十步连着看同一块屏幕：GDI 那一路从 10 × 29.5 ≈ 295 毫秒降到
  30 毫秒，桌面复制那一路从 10 × 2 ≈ 20 毫秒降到 2 毫秒。
- **查看间隔**（`intervalMs`）：一步两次看屏幕之间最少隔多久；等待类步骤拿它当轮询节奏，默认 50–200 毫秒
  留空，也就是按屏幕刷新一次的时间来看（60 赫兹 16 毫秒、240 赫兹 5 毫秒），一次轮询花掉上表里那一行
  的时间，乘上看了几次。屏幕刷新率是"看"这件事的硬下限：画面没重画，再看也只能读到同一张。

## 还没有的

- 节流是每步的（`MacroRunner._looked` 按步骤标识记），没有"整个宏每秒最多看几次"的总闸：十个不同的找图
  步骤挤在一个循环里，各自都不限速，总成本是它们之和。要让它们共用画面，得每一步都填 `frameMaxAgeMs`，
  而且共享的键是"来源 + 抓法"，设置里把读窗口或读屏幕换成另一档就不共享。
- 抓屏与匹配都在运行线程上同步做，那 29 毫秒是一次实打实的阻塞。宏本来就是顺序执行，所以它只让这一圈变长，
  不牵动别的步骤。
- 文字识别的模型加载每个进程一次，第一次"看"的时候付。

## 怎么再量一次

照「怎么量的」那一节搭个临时工程，引用 `WhaleGenie.Core`，用 `WindowsDeviceLayer` 取设备：

```csharp
using WhaleGenie.Core.Devices;
using WhaleGenie.Core.Devices.Platform;

var layer = new WindowsDeviceLayer();
var whole = layer.Screen.Capture(
    new ScreenCaptureRequest(0, 0, 2560, 1440, CaptureMethod.Gdi));

var needle = Cut(whole.Frame, 900, 500, 200, 80);   // 从刚抓到的那张画面上裁一块
var hits = layer.Vision.FindAll(whole.Frame, needle,
    new VisionQuery(MatchAlgorithm.Normed, 80, 6, null, 1));

var spans = layer.Ocr.Recognize(whole.Frame, "auto");
```

量之前把别的重活停掉（尤其别和整套 `dotnet format` 一起跑），并且用中位数，不要用单次。
