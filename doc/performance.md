# 性能测试

[简体中文](performance.md) | [English](performance.en.md)

"看一次屏幕"要花多少时间、触发器隔多久看一次，以及这些数字是在哪台机器上、用什么办法量出来的。它不随 CI
跑：改动画面获取（`WhaleGenie.GraphicsCapture`）、匹配与识别（`OpenCvVisionDevice`、`PixelSearch`、
`PaddleOcrDevice`、`OpenCvDetectDevice`）或触发器的等待间隔（`MacroTriggerService`）之后，在这里留一笔新的，好跟改动前比。数字
之外的事情——谁读屏幕、什么时候读——见
[manual.md](manual.md) 的「画面从哪来、怎么取」。

## 怎么量的

- 机器：桌面 2560×1440，16 核，Windows，`net10.0-windows10.0.19041` 的 Release 构建。
- 办法：临时建一个引用 `WhaleGenie.Core` 的小程序，直接用引擎自己的设备——`WindowsDeviceLayer` 的
  `Screen` / `Vision` / `Ocr`，与运行时走的是同一条路。每项先空跑一次热身，再取 6–15 次的中位数。小程序
  量完就删，不进仓库。
- 参考图是当场从整屏上裁下来的 200×80 一块，所以它一定找得到，量到的是"找得到"这一路的成本。
- 这些是这一台机器上的量级：换分辨率、换显卡、换 CPU 都会变。比数字本身更值得记住的是它们之间的比例。

## 抓一张画面

| 怎么抓 | 中位数 | 最快 / 最慢 |
| --- | --- | --- |
| 整屏 2560×1440，桌面复制（显卡交出的整块画面，画面重画过） | 2.0 ms | 0.5 / 7.6 |
| 同上，画面没有重画过（给的是手里那张） | 0.1 ms | 0.1 / 0.2 |
| 400×300，桌面复制 | 0.1 ms | 0.1 / 0.4 |
| 整屏 2560×1440，桌面（GDI） | 22.7 ms | 15.9 / 26.3 |
| 一小块 400×300，桌面（GDI） | 4.1 ms | 3.9 / 4.6 |
| 整屏 2560×1440，Graphics Capture | 10.1 ms | 8.7 / 15.7 |
| 同一块屏，每次读都开关会话（Graphics Capture） | 64.1 ms | 50.7 / 66.2 |
| 一个窗口 420×320，Graphics Capture | 5 ms | 3.8 / 25.8 |
| 同一个窗口，每次读都开关会话（Graphics Capture） | 44.3 ms | 37.7 / 58.4 |
| 一个铺满屏幕的窗口 2576×1416，窗口（PrintWindow） | 20 ms | 16 / 28 |
| 同一个窗口缩到 900×650，窗口（PrintWindow） | 4 ms | 3.6 / 5.5 |
| 一个窗口 420×320，窗口（PrintWindow） | 4.2 ms | 3.4 / 5.0 |

这一组是 2026-10 在这同一台机器上重新量的：那一次这块屏的桌面复制被一个远程桌面程序占着（第二次
`DuplicateOutput` 交不出来），所以**桌面复制那三行仍是更早一次量到的数**，其余各行走的是当时真能用的路。
"每次读都开关会话"两行量的是同一件事不做会话复用时的代价，见下面那段。

整屏最快的一条路是**桌面复制**（DXGI Desktop Duplication）：显卡正在往显示器合成的画面被复制进我们自己的
纹理里，读出来就是屏幕上那一张。画面重画过就付一次 14.7 MB 的搬运，2560×1440 是 2 毫秒，比 GDI 复制屏幕
快十几倍，并且独占全屏的游戏只有它能取到（GDI 给的是黑屏）。它还是唯一"画面没重画就白拿"的一条路：桌面
没动过就没有新帧，手里那张就是屏幕上那张，再要一次只要 0.1 毫秒——引擎里一次整屏"看"多数落在这一档上。
代价是每个进程第一次要建一次显卡设备（0.25 秒上下，一次运行付一次），而且显示器开着 HDR、或者屏幕是转着
用的时侯它读不了；那时读屏幕那一档是「自动」就退回 GDI，点名的档位则如实报出来（见「画面从哪来、怎么取」
那一节，读屏幕的「Graphics Capture」现在不在自动那一路里）。

GDI 这一路抓一次的成本跟"抓多大"走：抓整屏要把 2560×1440×4 ≈ 14.7 MB 从显示设备搬进内存，抓 400×300
只有它的十五分之一；那 23 毫秒里绝大部分是这次搬运（单独量 BitBlt 约 16 毫秒，取回内存 0.6 毫秒，分配
输出缓冲 0.6 毫秒）。桌面复制反过来跟抓多大没关系：它每次都要拿整块屏再裁出你要的那块，所以 400×300 与
整屏同一价钱（2 毫秒，画面没重画时 0.1 毫秒）。要一小块，GDI 那一路 4 毫秒也够快，好处是不用先建显卡
设备；所以抓得少、跑得短的宏，勾"桌面（GDI）"反而更划算。窗口（PrintWindow）这一路是靠请窗口把自己重画
一遍，所以也跟窗口多大走：铺满屏幕的窗口 20 毫秒，缩到 900×650 只要 4 毫秒。

Graphics Capture 是从合成器手里拿一帧画面：整屏 10 毫秒，比 GDI 复制整屏快一倍上下，代价是要先建一次显卡
设备与会话。窗口那一路跟窗口多大走，420×320 的窗口 5 毫秒，与 PrintWindow 的 4 毫秒同一量级。

**Graphics Capture 的会话要留着**：开一个会话要建显示设备与帧池，此后每一帧只是一次显存到内存的搬运。
留着会话读整屏 10 毫秒、读一个 420×320 的窗口 5 毫秒；每读一次就开一个、读完就关则分别要 64 毫秒与 44 毫秒，
差六到九倍，多出来的是每次重建那套东西。Windows 还会在正在被读的窗口或屏幕四周画一圈捕获提示边框，会话
开着就在、关掉就没——**每次读都开关会话，边框就会跟着一闪一闪**，这也是它必须留着的一个理由。分层窗口、
系统设置页、输入法候选框、显卡的覆盖层这些根本认不出的窗口只在第一次试一下就被记下来，不去为它们反复
开关会话。

## 在画面里找东西

参考图 200×80，画面都是整屏 2560×1440，除了注明的那一行：

| 找什么 | 中位数 |
| --- | --- |
| 找图，归一化相关 | 211 ms |
| 找图，相关 | 202 ms |
| 找图，平方差 | 201 ms |
| 找图，特征比对 | 281 ms |
| 找图，只在 640×480 里找（归一化相关） | 14 ms |
| 找色，颜色出现在画面开头 | ~0 ms |
| 找色，颜色不在画面上（走完全幅） | 2.5 ms |
| 找色，要离颜色最近的 20 个（走完全幅） | 11.9 ms |
| 找色并算占比，整屏（找一遍，再走一遍数像素） | 4.3 ms |
| 找色并算占比，400×300 | 0.2 ms |
| 多点找色，400×300（三个点，颜色不在画面上） | 0.2 ms |
| 判断画面有没有动（等画面静止的每一轮） | 5.7 ms |
| 文字识别，整屏 | 128 ms |
| 文字识别，800×200 | 23 ms |

- 找图的成本跟"搜索面积 × 参考图面积"走：整屏里找 200×80 是 211 毫秒，同一块参考图收进 640×480 去找
  只剩 14 毫秒，十五分之一。**把区域收小是这里最大的一根杠杆**，比换算法、比少抓一次屏都管用。
- 找色只看单个像素：命中出现得越早越便宜（第一个像素就中，量到 0 毫秒）；要"离颜色最近的几个"就得走完
  整幅，那是 12 毫秒。颜色根本不在画面上时，一次注定落空的查找是 2.5 毫秒。这两处都比改前快六倍上下，来得
  自同一件事：一个像素的颜色是否算数，看的是三个通道的平方和，与看距离是同一个问题，而由距离求值要开一次
  平方根，那一步是每个像素都要付的（同一条路 14.5 → 2.5 毫秒）。要"离颜色最近的几个"时比的是平方和，排
  出来的次序与按距离排一样，所以最贵的这一行也从 30 毫秒降到 12 毫秒。
- 算占比与多点找色都是把整块区域走一遍：整屏 2560×1440 数一遍是 2.5 毫秒，"找一遍再数一遍"是 4.3 毫秒；
  400×300 只要 0.2 毫秒。条件「颜色占比达到」走的是同一趟，所以它跟查找颜色问占比一样贵。**占比只在步骤
  真的问它时才数**，没问的步骤还是走"命中即返回"的那条路。
- 找色也量过 OpenCV 那条路（`InRange` 加 `CountNonZero`）。整屏数一遍 2.7 毫秒，与手写的平方和走法
  2.5 毫秒同一量级，但它比的是每个通道各给一个上下限的方框，与引擎的圆规则不是同一个判据：宽容度 5% 时
  多算 683 个像素，而引擎认的是 249 个；要拿回同一个答案还得在方框里再走一遍，共 3.8 毫秒。多点找色的
  三个点用 OpenCV 是三次 `InRange` 加两次按位与，400×300 上是 1.96 毫秒，比手写的 0.2 毫秒贵十倍，而且
  只说出"有几个"，要位置还得再找一遍。所以这条路没有走。
- 文字识别第一次调用要 1.1–10.3 秒把模型读进来（取决于磁盘缓存有多热），之后才是 128 毫秒。整屏识别是
  这里最贵的一次"看"。

## 用模型找物体（检测）

模型不随程序走，所以量的是一个公开的模型：yolov8n 的 ONNX 导出（12.8 MB，导出尺寸 640），画面是一张
810×1080 的照片，按检测那几步的办法缩放补边进 640 的正方形（2026-10，同一台机器，Release 构建）：

| 做什么 | 一次 | 十次运行 |
| --- | --- | --- |
| 一次检测（yolov8n，640） | 34–36 ms（每一遍最快的那一次） | 中位数 38–56 ms |
| 第一次检测（含读模型，之后一直留着） | 129–153 ms | — |

快的这一头很稳：每一遍跑十一趟，最快的一趟都在 34–36 毫秒；中位数飘到 50 上下不是模型的事，是机器上
还有别的进程在占 CPU。写宏时按"一次四十毫秒上下"估。检测的成本与模型大小、机器一起走：这一次是
640×640 走过 164 层，换成更大的模型（yolo11m、yolo11x 这类）会成倍变久。**它与搜索区域有多大基本
无关**：画面总是缩放补边成模型要的那个正方形，所以一屏与一小块代价一样——与找图正好相反，找图那
211 毫秒里绝大部分是"搜索面积 × 参考图面积"。**它也与画面里有多少东西基本无关**：多认出的几处只是
后面按置信度筛、按类做重叠抑制的那一小段（几千个候选，几十微秒）。区域更大只多花缩放那一次拷贝。

## 一次"看"合起来是多少

一次"看" = 抓一次画面 + 在上面做一次算法。每次重新抓屏时（`frameMaxAgeMs` 为 0；非等待步骤的
`intervalMs` 为 0），每看一次就重抓一次，于是：

| 做法 | 一次 | 每秒 |
| --- | --- | --- |
| 整屏找图 200×80 | 2.0 + 211 ≈ 213 ms | 约 5 次 |
| 同一件事只在 640×480 里找 | 4.4 + 14 ≈ 18 ms | 约 55 次 |
| 整屏找色（命中早） | 2.0 + 0.4 ≈ 2.4 ms | 约 400 次 |
| 整屏文字识别 | 2.0 + 128 ≈ 130 ms | 约 8 次 |
| 整屏检测一次（yolov8n，640） | 2.0 + 40 ≈ 42 ms | 约 24 次 |
| 等画面静止的每一轮 | 2.0 + 5.7 ≈ 8 ms | 约 125 次 |

两个能改变这个数的开关，都在「高级设置」里，默认都是关的：

- **接受多久以内的画面**（`frameMaxAgeMs`）：大于 0 时，同一次运行里同一来源、同一抓法的画面只抓一次，
  后面的步骤从这张画面上裁自己要的那块。十步连着看同一块屏幕：GDI 那一路从 10 × 29.5 ≈ 295 毫秒降到
  30 毫秒，桌面复制那一路从 10 × 2 ≈ 20 毫秒降到 2 毫秒。
- **查看间隔**（`intervalMs`）：一步两次看屏幕之间最少隔多久。等待类步骤拿它当轮询节奏，留空就是按
  屏幕刷新一次的时间来看（60 赫兹 16 毫秒、240 赫兹 5 毫秒）；`waitUntil.pollMs` 与
  `uia.waitElement.pollMs` 另有 200 毫秒默认值，非等待的看屏幕步骤默认 0。一次轮询花掉上表里那一行
  的时间，乘上看了几次。屏幕刷新率是"看"这件事的硬下限：画面没重画，再看也只能读到同一张。

## 还没有的

- 节流是每步的（`MacroRunner._looked` 按步骤标识记），没有"整个宏每秒最多看几次"的总闸：十个不同的找图
  步骤挤在一个循环里，各自都不限速，总成本是它们之和。要让它们共用画面，得每一步都填 `frameMaxAgeMs`，
  而且共享的键是"来源 + 抓法"，设置里把读窗口或读屏幕换成另一档就不共享。
- 抓屏与匹配对运行线程都是同步的：拿画面那一下（GDI 整屏 23 毫秒）在画面获取自己那条线程上做，运行线程等着，
  所以它仍是一段实打实的阻塞。宏本来就是顺序执行，所以它只让这一圈变长，不牵动别的步骤。
- 文字识别的模型加载每个进程一次，第一次"看"的时候付。

## 触发隔多久看一次

触发器不是"一发生就告诉你"，而是隔一会儿看一眼：像素颜色 60 毫秒、程序 30 毫秒、窗口 500 毫秒。看得比
"这件事持续多久"慢就会漏——一个程序起来了又退掉，两次看之间就没有它。

量法：临时写一个搭子，用真的 `MacroTriggerService`（真的 `WindowsDeviceLayer`、真的窗口、真的程序）
量"抓到了没有"。窗口由搭子自己在一条跑消息循环的线程上建起来、再关掉（建在不跑消息循环的线程上的窗口，
别的线程看不准）；程序是 `cmd.exe` 的一份改名副本，起一次就退出，`Process` 的句柄要立刻放开——留着它
能让已经退出的进程继续留在进程表里，量出来的是假的。结论（2026-10，同一台机器）：

| 要等的东西 | 活了多久 | 改之前 | 改之后 |
| --- | --- | --- | --- |
| 窗口出现并留在那儿 | — | 5/5，晚 300–350 毫秒 | 5/5，晚 1–4 毫秒 |
| 窗口关上 | — | 5/5，晚 315–333 毫秒 | 5/5，晚 2–3 毫秒 |
| 窗口亮 400 毫秒就走 | 400 ms | 5/5，晚 320–350 毫秒 | 5/5，晚 1–2 毫秒 |
| 窗口亮 100 毫秒就走 | 100 ms | **0/5，全漏** | 5/5，晚 1–2 毫秒 |
| 程序起完就退 | 33 ms（在进程表里只待 11–33 ms） | 20 例里 11 例 | 20 例里 19 例 |
| 程序活 100 毫秒上下 | 78–173 ms | — | 5/5 |

于是做了两件事。**窗口**改成由机器在出现、消失、改名时说一声（`WindowsWindowEvents`，
`SetWinEventHook`），听见就立刻读一遍窗口表；500 毫秒那一轮留着，是机器不肯说时的退路，也让"一开机就
开着"与轮询那一路一模一样。**程序**没有这样的消息可听：能说这件事的 WMI 事件订阅（`Win32_ProcessStartTrace`）
要管理员权限，实测非管理员下报「拒绝访问」，所以把读法改便宜——从"逐个打开进程读名字"（263 个进程 2.5
毫秒）改成只问一个名字（1.2 毫秒）——于是 30 毫秒一轮的代价与原来 60 毫秒一轮相同，而漏掉的少了一半多。
还想更稳只剩把间隔继续压小：10 毫秒一轮就是常驻一个核的一成，为一个 20 毫秒的程序付这个不划算，所以没
做成开关。

## 怎么再量一次

照「怎么量的」那一节搭个临时工程，引用 `WhaleGenie.Core`，用 `WindowsDeviceLayer` 取设备。
要单独量某一档抓法就把 `CaptureWay` 点出来，要看某一档是不是真的能用就直接拿
`WhaleGenie.GraphicsCapture` 的 `ScreenGrabber`：

```csharp
using WhaleGenie.Core.Devices;
using WhaleGenie.Core.Devices.Platform;
using WhaleGenie.GraphicsCapture;

var layer = new WindowsDeviceLayer();
var whole = layer.Screen.Capture(
    new ScreenCaptureRequest(0, 0, 2560, 1440, CaptureWay.Gdi));

// 或者直接问那一档：window 传 0 就是读屏幕，返回的 Used 是真正用了的那一档。
using var grabber = new ScreenGrabber();
var grab = grabber.Grab(0, 0, 0, 2560, 1440, CaptureWay.DesktopDuplication);

var needle = Cut(whole.Frame, 900, 500, 200, 80);   // 从刚抓到的那张画面上裁一块
var hits = layer.Vision.FindAll(whole.Frame, needle,
    new VisionQuery(MatchAlgorithm.Normed, 80, 6, null, 1));

var spans = layer.Ocr.Recognize(whole.Frame, "auto");

var found = layer.Detector.Detect(@"C:\models\yolov8n.onnx", whole.Frame,
    new DetectionQuery(ConfidencePercent: 25, InputSize: 640, IouPercent: 45));
```

量之前把别的重活停掉（尤其别和整套 `dotnet format` 一起跑），并且用中位数，不要用单次。
